ROS2에서 두 정수를 더해 돌려주는 간단한 서비스(service) 서버와 클라이언트를 만들어 봤어요. 요청을 보내면 응답이 오는 걸 확인하는 것까지는 교재 예제 그대로였는데, 그 예제에는 실제로 쓰면 서버를 멈추게 하는 구멍이 하나 있었습니다. 오늘은 그 구멍과 막는 방법을 정리해요.

## 서비스는 요청과 응답이 한 번씩 오가요

서비스는 토픽(topic)과 다르게 동작해요. 토픽은 카메라 영상처럼 한 방향으로 계속 흐르는 스트림이고, 서비스는 "이 값을 계산해 줘"처럼 한 번 요청하고 한 번 응답받는 왕복 통신이에요. 서버가 `create_service`로 콜백을 등록해 두면, 클라이언트가 요청할 때마다 그 콜백이 불려서 응답을 채워 돌려줍니다.

여기서 응답을 채우는 콜백이 이 이야기의 핵심이에요. 콜백은 요청 객체를 받아 계산한 뒤, 미리 만들어져 넘어온 응답 객체에 값을 넣고 그대로 반환해야 해요. 반환을 빠뜨리면 응답에 `None`이 나가서 클라이언트가 조용히 실패합니다.

## 콜백에서 예외가 나면 서버가 죽어요

문제는 콜백 안에서 예외가 던져질 때예요. rclpy는 콜백에서 발생한 예외를 실행기(executor)로 그대로 전파하고, 그러면 요청을 계속 처리하던 `rclpy.spin()`이 중단됩니다. 서버 노드 자체가 멈추는 거예요.

더 나쁜 건 클라이언트 쪽이에요. 서버가 예외로 멈추면 응답이 나가지 않는데, 클라이언트는 그 사실을 모른 채 응답을 기다립니다. 무한 대기에 걸린 프로세스는 죽은 프로세스보다 발견이 늦어서 더 곤란해요. 요청 하나가 서버를 멈추고 클라이언트까지 매달아 놓는 셈입니다.

## 흔한 방아쇠는 정수 범위예요

이 예외가 어디서 나는지 보면 감이 잡혀요. 두 수의 합을 응답의 `int64` 필드에 넣는데, 파이썬의 `int`는 자릿수 제한이 없는 반면 ROS2의 `int64`는 8바이트 고정이에요. 파이썬에서는 아무렇지 않게 계산되던 큰 수가 응답 필드에 대입되는 순간, 메시지 정의에서 생성된 검증 코드가 범위를 벗어났다며 예외를 던집니다. 입력이 조금만 커져도 서버가 죽을 수 있다는 뜻이에요.

## 콜백을 감싸서 죽지 않게 만들어요

그래서 콜백 전체를 `try`로 감싸는 게 이 서버 코드에서 가장 중요한 부분이 됩니다. 값을 대입하기 전에 범위를 직접 검사하고, 벗어나면 예외를 잡아 실패를 기록한 다음 안전한 기본값을 응답에 넣어요.

```python
INT64_MIN, INT64_MAX = -(2**63), 2**63 - 1
try:
    result = request.a + request.b
    if not (INT64_MIN <= result <= INT64_MAX):
        raise OverflowError('결과가 int64 범위를 벗어남')
    response.sum = result
except OverflowError as exc:
    self.get_logger().error(str(exc))
    response.sum = 0
except Exception as exc:
    self.get_logger().error(f'처리 실패: {exc}')
    response.sum = 0
return response
```

넓은 범위의 `except`는 보통 피해야 할 패턴이지만, 서비스 콜백에서는 "죽지 않고 응답은 돌려준다"가 더 중요해서 예외적으로 허용해요. 대신 반드시 로그에 원인을 남겨 나중에 추적할 수 있게 합니다.

한 가지 남는 문제가 있어요. 실패했을 때 `sum`에 0을 넣으면, 클라이언트는 그게 정말 합이 0인지 실패해서 0인지 구분할 수 없습니다. 그래서 실무에서는 응답에 `bool success`와 `string message` 필드를 함께 둬요. 오늘 같이 만든 모터 on/off 서비스의 응답은 이미 그 형태로, 성공 여부와 사유 문자열을 함께 돌려줍니다.

## 클라이언트도 자신을 지켜야 해요

서버만 고쳐서는 부족해요. 클라이언트가 무한 대기에 빠지지 않으려면 두 곳에 타임아웃을 걸어야 합니다. 서버가 올라올 때까지 기다리는 `wait_for_service`에 제한 시간을 주고, 응답을 기다리는 `spin_until_future_complete`에도 제한 시간을 줘요. 시간 안에 응답이 오지 않으면 요청을 취소하고 실패로 처리합니다.

응답을 꺼낼 때도 조심해야 해요. `future.result()`는 호출이 실패하면 `None`을 돌려주는데, 확인 없이 곧바로 `response.sum`에 접근하면 이번엔 클라이언트가 예외로 죽어요. 결과가 `None`인지 먼저 보고 접근하는 습관이 필요합니다.

정리하면 서비스는 두 규칙으로 지켜요. 서버는 콜백을 감싸 어떤 요청에도 죽지 않고 응답을 돌려주고, 클라이언트는 타임아웃으로 무한 대기를 끊어냅니다. 계산 로직 몇 줄보다 이 두 방어를 갖추는 게 실제로 돌아가는 서비스에 훨씬 가까운 일이었어요.
