색 기반 검출은 시작하기 쉬워요. HSV 범위 하나만 정하면 파란 상자를 찾을 수 있으니까요. 대신 조명이 바뀌거나 비슷한 색이 배경에 있으면 바로 흔들리고, 무엇보다 "이 색"이 아니라 "이 물체"를 찾고 싶을 때 확장이 막힙니다. 검출기를 YOLO로 바꾸는 작업을 하면서 두 가지 접근을 차례로 시험했어요.

## zero-shot은 합성 장면에서 약했어요

먼저 시도한 건 open-vocabulary 계열인 YOLO-World예요. 학습 없이 텍스트로 클래스를 지정할 수 있어서, `blue box` 같은 문장만 주면 바로 검출이 되는 모델이에요.

```python
m = YOLO('yolov8s-worldv2.pt')
m.set_classes(['blue box', 'red box', 'green box'])
r = m.predict(img, conf=0.05)[0]
```

결과는 기대와 달랐어요. 화면 안의 3cm 큐브(약 15~40픽셀)는 잡지 못하고, 대신 로봇의 노란 팔을 `blue box`로 잡았어요. 신뢰도도 0.15와 0.08로 사실상 노이즈였습니다. 거리를 좁혀 큐브가 커진 장면에서도 팔을 `green box`로 잡는 건 마찬가지였어요.

이유는 학습 분포예요. 이런 모델은 웹 사진으로 학습해서 실사 질감과 맥락에 맞춰져 있는데, 게임 엔진 렌더링에 가까운 합성 이미지는 텍스처도 그림자도 다릅니다. 작은 객체 검출이 원래 어려운 문제라는 점까지 겹치면 신뢰할 수 없는 출력이 나와요. zero-shot은 "무엇이든 찾아준다"기보다 "학습 분포 안에서 이름표를 유연하게 붙여준다"에 가깝습니다.

## 시뮬레이터는 정답을 알고 있어요

여기서 시뮬레이션 환경의 이점이 드러나요. 실제 세계에서 학습 데이터를 만들려면 사람이 이미지마다 상자를 그려야 하는데, 시뮬레이터에서는 물체의 위치와 색을 시스템이 이미 알고 있습니다.

이 프로젝트에서는 큐브가 단색이라 HSV 마스크가 사실상 진리값 역할을 했어요. 큐브 세 개를 매번 무작위 위치로 옮기고, 로봇도 조금씩 회전시킨 뒤 화면을 캡처하고, 같은 프레임에서 색 마스크의 연결 성분 경계 상자를 라벨로 저장하는 방식이에요.

```python
for name in ('pick_blue', 'pick_red', 'pick_green'):
    set_pose(name, random.uniform(0.40, 1.35), random.uniform(-0.55, 0.55), 0.015)
img = capture()
for cls in (0, 1, 2):
    for x, y, w, h in hsv_bboxes(img, cls):
        lines.append(f'{cls} {(x+w/2)/W:.6f} {(y+h/2)/H:.6f} {w/W:.6f} {h/H:.6f}')
```

주의할 점은 라벨에 로봇 자신이 섞이는 것이었어요. 차체 상판이 빨간색이라 `red_box` 라벨로 들어가면 학습이 망가집니다. 화면 하단에 닿아 있고 폭이 큰 성분은 자기 몸으로 보고 제외하는 규칙을 넣어 걸렀어요.

150장을 만드는 데 5분, YOLOv8n 파인튜닝에 GPU로 3분이 걸렸습니다. 학습은 125장으로 하고 25장을 검증에 남겨 60에폭을 돌렸어요. 검증 지표는 mAP50 0.98, 정밀도 0.99가 나왔습니다.

```
                   all         25         58      0.991      0.919      0.981      0.799
```

파이프라인에 연결한 뒤 실제 주행 중 검출 신뢰도는 0.79에서 0.94 사이였어요. zero-shot의 0.08~0.15와 비교하면 같은 장면에서 완전히 다른 수준입니다.

## 무엇이 검출을 만들었는지 로그로 남기기

검출기를 바꾸면서 같이 넣은 게 근거 로그예요. 이전에 색 필터를 쓸 때, 파란색 지정과 빨간색 지정이 서로 다른 실행인데도 완전히 같은 검출 좌표를 내는 일이 있었어요. 두 색 범위는 겹치지 않으니 원래 불가능한 결과였고, 실제로 그 검출은 색 필터가 만든 게 아니었습니다.

선택된 영역의 실제 픽셀 값을 한 줄 찍어두면 이런 착각이 바로 드러나요.

```
검출 근거: HSV평균=(113,163,206) 면적=223px     ← 파랑(H 113)
검출 근거: HSV평균=(0,163,206) 면적=230px       ← 빨강(H 0)
```

YOLO로 바꾼 뒤에도 같은 자리에 클래스와 신뢰도를 남깁니다. 검출기가 블랙박스일수록 "무엇을 보고 그 판단을 했는지"를 로그에 남겨야 결과를 신뢰할 수 있어요.

```
검출 근거(YOLO): green_box conf=0.90 d=0.73
```

## 대신 분포 밖에서는 여전히 약해요

파인튜닝 모델이 만능이 되는 건 아니에요. 이 모델은 원거리에서 작게 보이는 큐브로만 학습했기 때문에, 손목 카메라가 물체를 가까이서 크게 담는 장면은 학습 분포 밖이에요. 실제로 근접 정렬 단계는 색 기반 검출을 그대로 두고, 접근 단계만 YOLO로 바꿨습니다.

시뮬레이션 데이터로 학습한 모델을 실물에 옮길 때 성능이 떨어지는 문제를 도메인 갭(domain gap)이라고 부르는데, 여기서 확인한 건 그 갭이 실물과 시뮬 사이에만 있는 게 아니라 같은 시뮬 안에서도 카메라와 거리 조건이 바뀌면 생긴다는 점이에요. 자동 라벨링의 진짜 이점은 이 갭이 보일 때마다 그 조건으로 데이터를 다시 뽑아 몇 분 만에 재학습할 수 있다는 데 있습니다.

지금 구조에서 새 물체를 추가하는 비용도 같은 이유로 낮아요. 물체를 장면에 올리고 생성 스크립트를 다시 돌린 뒤 재학습하면 되니까, 사람이 상자를 그리는 단계가 아예 없습니다. 색이 단색이 아니어서 마스크로 진리값을 만들 수 없는 물체라면, 시뮬레이터가 알고 있는 물체 자세와 카메라 파라미터로 경계 상자를 직접 투영하는 방법으로 바꿔야 해요.

## 설치 단계에서 만난 함정

패키지 설치도 그냥 지나가지 않았어요. `ultralytics`를 설치하면 의존성으로 NumPy 2.x가 따라 들어오는데, ROS의 `cv_bridge`는 NumPy 1.x ABI로 빌드돼 있어서 이후 모든 이미지 콜백이 깨집니다.

```
A module that was compiled using NumPy 1.x cannot be run in NumPy 2.5.1
```

`numpy<2`로 되돌리면 해결되지만, PyTorch를 다시 설치하면 NumPy가 또 올라오기 때문에 순서에 주의해야 해요. GPU 빌드로 교체할 때도 같은 일이 반복돼서, 설치가 끝날 때마다 버전을 다시 고정해야 했습니다.

로보틱스 환경에서 파이썬 패키지를 추가할 때는 설치 직후 `cv_bridge` 임포트가 여전히 되는지 확인하는 습관이 필요해요. 딥러닝 패키지는 최신 NumPy를 원하고 ROS 배포판 바이너리는 빌드 시점 버전에 묶여 있어서, 두 생태계를 한 인터프리터에 얹는 순간 이 충돌은 예정된 것에 가깝습니다.

```python
import numpy, torch
from cv_bridge import CvBridge     # 설치 후 매번 확인하는 한 줄
```
