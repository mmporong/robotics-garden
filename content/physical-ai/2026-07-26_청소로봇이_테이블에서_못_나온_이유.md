청소로봇이 테이블 아래로 들어갔다가 못 나오는 영상을 봤어요. 다리 사이에 몸이 낀 것도 아닌데 같은 자리를 계속 맴돌더라고요.

커뮤니티에서는 세 가지 추측이 나왔어요. 인플레이션 레이어 크기가 절묘하게 길을 막는 것 같다, 로봇이 커서 그렇다, 장애물 크기가 왔다 갔다 한다. 셋 다 그럴듯해서 AI와 같이 내비게이션 스택 소스를 열어 하나씩 확인해봤어요.

## 먼저 짚어둘 전제

영상 속 로봇이 어떤 소프트웨어를 쓰는지는 알 수 없어요. 상용 청소로봇은 대부분 자체 내비게이션 스택을 쓰고 내부를 공개하지 않아요. 그래서 아래 내용은 "저 제품이 이렇게 동작한다"가 아니라, 코스트맵 기반으로 경로를 짜는 로봇이라면 같은 증상이 어떤 경로로 만들어지는지에 대한 설명이에요.

근거는 소스가 공개된 Nav2에서 가져왔어요. ROS2 쪽 표준 내비게이션 스택이고 코스트맵 처리 방식이 잘 문서화돼 있어서, 확인 가능한 참조 구현으로 쓰기 좋아요.

## 253이라는 값

경로를 계산하는 쪽에서 로봇은 크기가 없는 점이에요. 대신 장애물을 로봇 크기만큼 미리 부풀려 두고, 부풀린 격자 위에서 점을 움직여요. 점이 안전한 경로가 곧 실제 로봇이 안전한 경로가 되는 방식이에요.

부풀릴 때 쓰는 값은 `nav2_costmap_2d/include/nav2_costmap_2d/cost_values.hpp`에 정의돼 있어요.

```
NO_INFORMATION              255
LETHAL_OBSTACLE             254
INSCRIBED_INFLATED_OBSTACLE 253
MAX_NON_OBSTACLE            252
FREE_SPACE                    0
```

여기서 253은 "이 칸에 로봇 중심이 오면 몸이 반드시 장애물과 겹친다"는 뜻이에요. 장애물 자체인 254와는 다른 값이지만, 경로를 찾는 입장에서는 둘 다 갈 수 없는 칸이에요.

비용을 매기는 규칙은 `inflation_layer.hpp`의 `computeCost`에 있어요. 거리에 따라 세 갈래로 나뉘어요.

```cpp
if (distance == 0) {
  cost = LETHAL_OBSTACLE;
} else if (distance * resolution_ <= inscribed_radius_) {
  cost = INSCRIBED_INFLATED_OBSTACLE;
} else {
  double factor = exp(-1.0 * cost_scaling_factor_ *
                      (distance * resolution_ - inscribed_radius_));
  cost = (INSCRIBED_INFLATED_OBSTACLE - 1) * factor;
}
```

찾아보는 과정에서 하나 걸렀어요. 검색으로 나오는 문서 중에 `INSCRIBED_INFLATED_OBSTACLE`이 254라고 적힌 게 있는데, 현재 소스는 253이에요. 254는 `LETHAL_OBSTACLE`이고요. 오래된 문서를 그대로 인용하면 두 값이 겹쳐 보여서 한참 헤매게 돼요.

## 길을 막는 건 어느 파라미터인가

커뮤니티의 첫 번째 추측을 여기서 정정할 수 있어요. 방향은 맞는데 파라미터가 달라요.

`inflation_radius`(기본값 0.55)는 비용 그라데이션을 얼마나 멀리까지 칠할지 정해요. 이 범위 안에는 252 이하 값이 지수적으로 깔리고, 경로 계획은 이걸 "가급적 피해라"로 읽지 "못 간다"로 읽지 않아요.

통로를 실제로 지우는 건 `inscribed_radius`예요. 로봇 풋프린트에 내접하는 원의 반지름이고, 이 안쪽은 조건 없이 253이 돼요. 그리고 이 값은 보통 직접 지정하지 않고 풋프린트에서 자동으로 계산돼요. `inflation_layer.cpp`의 `updateInscribedRadius`가 `layered_costmap_->getInscribedRadius()`를 가져다 쓰는 구조예요.

**즉 통로를 닫는 건 인플레이션 반경이 아니라 로봇 치수예요.** 두 번째 추측인 "로봇이 커서 그렇다"가 정확히 이 지점을 짚은 거였어요.

## 1cm가 0이 되는 순간

다리 두 개가 간격 G로 서 있고 내접 반경이 r이라면, 통로가 열리려면 G가 2r보다 커야 해요.

반경 0.22미터인 로봇이면 간격이 0.44미터를 넘어야 해요. 로봇 지름이 0.44미터니까 여기까지는 상식적이에요.

문제는 여유가 근소할 때예요. 간격이 0.45미터면 남는 폭이 0.01미터인데, 코스트맵은 격자라서 한 칸이 보통 0.05미터예요. 0.01미터짜리 틈은 격자로 나누는 순간 한 칸도 안 남아요. 물리적으로는 1센티미터가 있는데 계산상으로는 0이 되는 거예요.

"절묘하게 막힌다"는 표현이 여기에 딱 맞아요. 조금만 넓었으면 지나갔을 곳이 이산화 때문에 사라져요.

## 관측도 흔들려요

세 번째 추측은 인플레이션이 아니라 obstacle layer 쪽 이야기예요.

obstacle layer는 센서 광선이 무언가에 맞으면 그 끝점을 장애물로 표시하고, 광선이 통과한 경로는 비어 있다고 지워요. 지우는 건 광선이 실제로 통과했을 때만 일어나고요.

테이블 다리는 이 구조에서 까다로운 대상이에요. 지름 3~5센티미터쯤 되는 얇은 기둥이라 2D LiDAR 광선이 몇 개나 맞을지가 거리와 각도에 따라 달라져요. 멀면 광선 간격이 벌어져 통째로 놓치고, 가까우면 여러 칸에 걸쳐 잡혀요. 게다가 다리 뒤쪽은 다리에 가려 광선이 못 가니까 한 번 잘못 찍힌 칸이 잘 안 지워져요.

한 칸 크게 잡히면 253 영역이 사방으로 한 칸씩 넓어져요. 아슬아슬하던 통로는 그 순간 닫히고요.

## 들어갈 땐 열려 있었어요

이제 영상의 순서가 설명돼요.

멀리 있을 때는 다리가 잘 안 잡혀서 통로가 열려 보이고, 경로 계획은 테이블 아래를 지나는 길을 내요. 로봇이 들어가요. 가까워지면 다리가 제대로 잡히면서 253 영역이 자라는데, 이때 로봇은 이미 안에 있어요. 안에서는 사방의 다리가 전부 근거리에서 관측되니까 로봇을 둘러싼 칸이 전부 253이 되고, 나가는 경로를 계산할 수 없게 돼요.

그다음이 흥미로워요. 경로를 못 찾으면 복구 동작이 도는데 그중에 코스트맵을 비우는 동작이 있어요. 비우면 장애물이 지워지니 다시 길이 열린 것처럼 보이고, 로봇이 움직이면 센서가 다시 다리를 봐서 또 닫혀요. 열리고 시도하고 닫히고 복구하는 순환이 밖에서는 서성이는 모습으로 보이는 거예요.

복구 동작이 근본 원인을 못 고친다는 게 여기서 드러나요. 관측을 지울 뿐 관측이 다시 들어오는 걸 막지는 못하니까요.

## 그럼 어떻게 푸나

원인이 셋으로 갈리니 손대는 곳도 달라요. 아래는 Nav2 문서와 소스를 근거로 정리한 방향이고, 실제 기체에서 검증한 값은 아니에요.

| 원인 | 조치 | 대가 |
|---|---|---|
| 풋프린트가 실제보다 큼 | `robot_radius` 또는 `footprint`를 실측값으로 | 너무 줄이면 실제로 부딪혀요. 범퍼 두께는 남겨야 해요 |
| 이산화로 통로 소멸 | 코스트맵 `resolution`을 0.05에서 0.025로 | 칸 수가 네 배라 연산량과 메모리가 늘어요 |
| 그라데이션이 과함 | `inflation_radius` 축소 (기본 0.55) | 좁은 곳은 통과하지만 벽에 붙어 다녀요 |
| 비용 경사가 가파름 | `cost_scaling_factor` 조정 (기본 10.0) | 253 영역은 안 줄어요. 그 바깥만 완만해져요 |
| 관측 요동 | 높이를 구분하는 voxel layer 도입 | 3D 센서가 필요해요 |
| 애초에 들어가면 안 되는 곳 | 진입 금지 영역 지정 | 근본 해결은 아니지만 가장 확실해요 |

하나 주의할 점은 `inflation_radius`를 `inscribed_radius`보다 작게 잡으면 안 된다는 거예요. 253 판정은 `inscribed_radius` 기준이라 그대로 남는데 바깥 그라데이션이 사라져서, 경로가 벽에 딱 붙게 돼요. 두 값은 항상 같이 봐야 해요.

찾아보니 실제 제품들은 마지막 줄을 택하는 경우가 많다고 해요. 파라미터를 아슬아슬하게 조여 통과시키는 것보다, 못 나올 곳에 안 들어가게 막는 편이 현장에서 안전하니까요.

## 아직 확인하지 못한 것

이 글은 영상 관찰과 공개 소스를 대조해 세운 설명이에요. 직접 로봇을 테이블 밑에 넣고 코스트맵을 띄워 253 영역을 눈으로 확인한 단계는 아니에요. 위 표의 조치들도 문서상 근거로 방향을 잡은 것이지 실측으로 효과를 잰 건 아니고요.

그래도 하나 분명해진 게 있어요. 이 현상에는 버그가 없어요. LiDAR는 자기가 볼 수 있는 평면만 정직하게 봤고, 인플레이션은 로봇 크기만큼만 정확히 부풀렸고, 경로 계획은 253을 피하라는 규칙을 그대로 지켰어요. 각 단계가 설계대로 동작한 결과가 끼임이고, 그래서 로그에 아무것도 안 남아요.

로봇 치수를 적는 파일에 숫자 하나를 크게 적으면 주행이 안 될 수 있다는 것도 같이 알게 됐어요. 나중에 직접 띄워보면서 그 숫자를 바꿔가며 253 영역이 어떻게 변하는지 확인해볼 생각이에요.
